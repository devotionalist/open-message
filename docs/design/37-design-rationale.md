# 设计合理性说明（强制）

**已定**：凡**角色设计、流程设计、组件设计、功能设计**，必须在权威文档中给出**合理性说明**；无说明不得冻结、不得标生产级完成（[36](./36-production-grade-bar.md)）。  
聊天里的「因为……」不算数，须落入 `docs/design/*` / `architecture` / `docs/user`（对外语义）对应落点。

审计维：[28 §3.1](./28-design-audit-requirements.md)。  
对照目标：[34](./34-architecture-goals.md)；硬约束：[00](./00-principles.md)。

---

## 0. 适用范围

| 类别 | 什么算「一项设计」 | 合理性落在哪 |
|---|---|---|
| **职责边界** | 组件/流程谁做谁不做 | [35](./35-component-roles.md)；跨角门禁见 L4 |
| **角色（组件内）** | Proxy、Owner、Standby、AR、各 Store… | [35](./35-component-roles.md) 每角色含「为何存在」；细章可加深 |
| **流程** | [13](./13-flows-and-diagrams.md) 目录表每一 ID | 本节或对应细章「为何合理」+ 图 |
| **组件** | Broker、Meta、Bookie、SDK… | 组件细章 §「为何合理」；摘要可在 35 |
| **功能** | 细章能力（幂等、Offload、四模式…） | 该细章 §「为何合理」；跨章能力在 29 问题→解法表 |

## 1. 合理性说明最低模板（必须可勾选）

每项设计正文中须能回答（标题可用「为何合理」或等价小节）：

```text
1. 要解决的问题（若不做，谁痛、什么坏）
2. 为何选此方案（对齐 00 硬约束 / 34 四目标中的哪几条）
3. 显式放弃的替代方案（至少 1 个）及放弃理由
4. 代价与已接受风险（窗口、重复、运维负担等）
5. 如何验收「合理成立」（测/演练/不变量；可指向场景 ID）
```

**不合格示例**：只写「参考 Pulsar」无问题；只写机制无代价；无放弃方案。

**合格直觉**：读者不看实现也能判断「为什么不是双主 / 为什么不搬盘 / 为什么 Proxy 必做」。

## 2. 四类对象的特化要求

### 2.1 角色设计

| 角色类 | 必答 |
|---|---|
| 组件角色 | 若不设该角色，职责会错误落到谁？禁止边是什么？ |

### 2.2 流程设计

| 必答 |
|---|
| 该流程守护哪条不变量（单主、Qa、尾唯一、at-least-once…）？ |
| 失败半步如何补偿（对应 00 §4）？ |
| 对用户观感（无感/可重试）如何交代（34 §4 / 33）？ |

### 2.3 组件设计

| 必答 |
|---|
| 权威状态在哪？为何不在别处？ |
| 扩容时并行度如何升、是否搬历史消息体（00 §5）？ |
| 与 OM/OL 边界是否违反 [19](./19-open-ledger-integration.md)？ |

### 2.4 功能设计

| 必答 |
|---|
| 归属里程碑与对外承诺是否诚实（尤其幂等）？ |
| 与已有功能正交还是重叠？重叠如何消解？ |
| 缺省关闭时系统是否仍满足硬约束？ |

## 4. 门禁

| 门禁 | 条件 |
|---|---|
| 设计冻结 | 范围内每项角色/流程/组件/功能均有合理性说明（本模板五问） |
| 审计 28 §3.1 | 无说明 = 合理性维发现项 |
| 生产级 36 | 「完整」含合理性；仅机制罗列不算生产级设计 |
| 新增 PR（设计） | 检查单含「已写为何合理 / 已列放弃方案」 |

## 5. 架构师自检

```text
[ ] 新组件角色 → 35 含合理性
[ ] 新流程 → 13 挂号 + 为何此序/此补偿
[ ] 新组件 → 细章或 35 含权威落点理由
[ ] 新功能 → 细章五问 + 29 表行（若新问题）
[ ] 放弃方案已写；代价已写；验收指针已写
```

缺对应 L4 门禁 → 不得宣称生产级，见 [36](./36-production-grade-bar.md)。

## 6. 组件角色合理性（摘要，细则 [35](./35-component-roles.md)）

| 角色 | 若不设 | 为何此职能 | 放弃方案 |
|---|---|---|---|
| **Proxy** | 地址风暴；公网难直连 Owner | 统一入口+转发；无持久消息 | 「无状态就不需要网关」 |
| **Owner** | 双写分叉 | 单 writer 排序+Qa Receipt | 多活同时成功写 |
| **Standby** | 冷切窗口长 | 预热缩短 RTO；仍 Fence | 双 Primary |
| **ManagedLedger** | 业务与存储纠缠 | 只编排链+赋序；Meta 在 OL | Broker 自管 LedgerMeta |
| **OL Client/Bookie/AR** | 无耐久闭环 | 存储权威与补副本 | Broker 内再造 AR |
| **Ownership/Index/Cursor Store** | 状态随进程丢 | 外置可迁可分片 | Broker 本地权威盘 |
| **Dispatcher** | 四模式无法统一 | 同日志多订阅语义 | 每模式一份存储 |
| **SDK** | 用户自写重试易错 | 默认重试+幂等字段 | 裸协议当默认 |
| **Admin/LoadManager** | 只能杀进程迁主 | 受控 Unload/密度 | SSH 改 Meta |

## 7. 流程合理性（摘要，图见 [13](./13-flows-and-diagrams.md)）

| ID | 流程 | 守护什么 | 为何此序 | 放弃方案 |
|---|---|---|---|---|
| P1 | Produce | Qa 后才 Receipt | Lookup→Owner→Append→Qa | 未达 Qa 先成功 |
| C1 | Consume+Ack | 位点外置；permits 背压 | Flow 后推送；Ack 刷 Cursor | 无许可狂推 |
| F1 | 冷切主 | 至多一主；尾唯一 | 租约→Acquire→Fence→Recover→Ready | 旧主继续写成功 |
| F2 | Drain/Unload | 计划内近无感 | 先停写再放权 | 默认 kill -9 |
| R1 | Fence+Recover | 全局同一 lastEntryId | OL 算法权威 | Broker 猜 Bookie 本地尾 |
| L1 | 滚本三步 | 跨系统非原子可补偿 | Close/Create→再挂 Index | 跨 OM+OL 单 CAS |
| PX | Proxy 路径 | 用户无感入口 | 缓存 Lookup+转发 | 业务枚举 Broker |
| ID | 幂等 | 重试不重复（分阶段） | seq 去重；M3 进 Meta | 默认宣称 exactly-once |
| WS | Promote | 缩窗口仍单主 | 早探测+CAS+Fence | 等满 TTL 或跳 Fence |
| OR | MarkOrphan | 防盘泄漏且不误删 | 显式标记+grace | 抽样 Index 就删 |
| OF | Offload | 热路径不写对象存储 | CLOSED 后卸；location 在 OL | 主写对象存储 |
| DM | 双 Meta 对账 | 非原子世界可发现缺口 | 全量引用 diff | 假装两套 Meta 原子 |
| UX | 用户无感 | 应用不人工修集群 | SDK 重试+Proxy | 要求业务改 Owner IP |
| S1–S3/SI | 扩缩容 | 加节点抬并发不搬历史 | 迁 ownership / 新 ledger | 搬历史消息体 |

## 8. 功能合理性（与 [29](./29-architecture-spec-catalog.md) 对齐）

功能级「问题→为何如此解」以 **29 §2** 为目录；每行对应细章必须有完整五问（或本章 §1 模板）。  
新增功能：先补 29 一行 + 细章「为何合理」，再实现。

**细章已有 `## 1. 为何合理` 的**（01–09 等）：视为达标，审计抽查五问是否齐全。  
**仅有「为何需要 / 目标」的**（如 14、15、23）：须在下一次改章时升格为五问模板，或显式引用本章对应行。
